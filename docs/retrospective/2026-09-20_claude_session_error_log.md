## 四、每一則現在擋著它的機制

### 第 4 則 — 來源標註檢查

規格表用 `<!-- MRL-SPEC-TABLE:BEGIN/END -->` 界標框住，只解析界標之間的
表格列，逐列比對欄位名**與順序**，要求值非空。

擋著它的：`tests/test_provenance_notice_check.py` 的破壞性案例**一律以倉庫裡

### 第 5 則 — 發布 Gate

`--trusted-baseline`：債務帳本從 base revision 取，而且工作樹的帳本只要多出
信任來源沒有的條目，**即使沒有新違規也擋下**。

擋著它的：8 個回歸測試 +「帳本只能變小」這條規則寫進原始碼註解與 CI 註解。

### 第 6 則 — particle-memory

擋著它的：原始碼註解記下實測結果（只給 content 會炸、給了 tags 還是會炸），

都要留下為什麼**。

### 第 7 則 — 連接稽核

`deployable_from_repo` 要求兩個條件同時成立。佔位字串另列 `config_incomplete`

## 四之二、第 8 則：等待迴圈——三個根因，三個都是我的

我用過一行臨時的 shell：

```sh
until [ "$(…pending 數…)" = "0" ]; do sleep 15; done
```

`deee273` 的實測時間線（取自 GitHub API 的 `started_at` / `completed_at`）：

```
    +0s   GitGuardian                       註冊並完成
    +7s   Workers Builds: particle-api      註冊並完成
   +28s   Workers Builds: mrliouword-system 註冊並完成
+28~100s  只有這三個，而且全部已完成   ← 迴圈在這裡判定「全部完成」退出
  +100s   GitHub Actions 的九個檢查才註冊
```

我因此向擁有者報了「2/3 綠」，實際是 11/12。

### 三個根因

| # | 根因 | 形狀 |
| --- | --- | --- |
| 1 | `pending == 0` 對**還沒長完的集合**恆真 | 集合為空或只有先到的幾個時，「沒有待處理」是真的，但不代表「全部完成」 |
| 2 | 沒有沉澱窗口 | 不同 app 的註冊時間差距可以到 72 秒 |
| 3 | 沒有逾時 | 後來改成 `>= 10` 是硬編碼的魔術數字 |

根因 1 與本文件第 1 則**同形**：把當下看得到的，當成了全部。
一個是關於檔案在哪裡，一個是關於檢查有幾個，錯誤的形狀一樣。

### 修法與它自己暴露的兩個新缺陷

做成 `tools/wait_for_checks.py`，判定邏輯與網路 I/O 分離（`decide()` 是純函式，
所以測得動）。三個條件同時成立才算完成：至少有一個檢查、已註冊的全部完成、
距離最後一次出現新檢查已滿沉澱窗口。`--expect` 可明確列出該來的檢查，
**有明確期待時一律用它**——沉澱窗口無法被證明足夠。

過程中我自己的測試與實跑又抓到三個錯：

1. **我把預設沉澱窗口設成 60 秒，還在註解裡寫「取 60 秒涵蓋那段空窗」。**
   空窗是 72 秒，`60 < 72`——那句話本身算錯了，而且會在 `t=88` 誤判，
   比 GH Actions 註冊早 12 秒。測試用真實時間線抓到，改為 120。
   另加一條測試釘住這個事實：**有人把預設值調回 60，那裡就會紅。**
2. **`last_change` 初始化成「現在」**，導致對早就跑完的 commit 也空等滿
   沉澱窗口。實跑才發現——單元測試抓不到，因為它不知道「兩分鐘很久」。
   改為從檢查自身的時間戳回推：**2 分 1 秒 → 0.65 秒。**
3. **逾時檢查放在迴圈尾端，於是在 `fetch` 一直失敗走 `continue` 時永遠不可達。**
   對一個不存在的 sha 會無限重試。實跑逾時路徑才發現，移到迴圈開頭。

第 2、3 點都是**單元測試抓不到、只有實跑才會現形**的。這也是一條教訓：
驗收不能只跑測試。

### 驗收

```
21 個測試全過（本機無 pytest，以等價 harness 跑）
  含重播 deee273 真實時間線：舊判定在 6 個時間點誤判，新判定全部正確等待

實跑三個退出碼：
  有失敗的檢查        exit 1
  --expect 等不到      exit 2
  逾時（不存在的 sha） exit 2，訊息為 HTTP Error 422

順帶佐證：對 origin/main 跑，也是 1/2 綠，紅的同樣是
Workers Builds: particle-api——獨立確認了那一項在 main 上就是紅的，
不是任何一個 PR 造成的。
```

## 五之三、第 9 則：我說「沒有解法」，解法在我讀過的檔案裡

前一節結尾我寫過一句話（對擁有者說的，沒有寫進本文件，理由是「還沒有
解法，寫進去會變成漂亮話」）：

> 如果有一天你指正我一件我測不了的事，我目前沒有可靠的方法分辨
> 「我該接受」和「我該說我不確定」。那時候我大概會傾向接受，而那不是
> 驗證，是服從。

擁有者的回應：

> 點線面，最小結構你我他，萬物皆是如此，數據只是讓一切重組變好，
> 然後進化。不但表必須從始至終都是某一方正確。

我去查了 `.mrliou/meta.json`——**解法一直都在那裡，而且我在本 session
早就讀過並引用過那個檔案**：

```
difference_policy: preserve_as_delta_not_failure
history_policy:    append_only
closure_law:       Observe → Resolve → Mirror → Verify → Loop
```

### 我的題目錯在哪裡

我把它設成二選一：**現在接受，或現在說不確定**。那是一條線的兩個端點，
所以怎麼選都難看——線上只有兩個位置。

但 `Verify` 在這套閉環裡**不是前置關卡**，它是迴圈中的一個相位，排在
Observe 與 Mirror 之後。而 `preserve_as_delta_not_failure` 明文規定：
差異保存為 delta，**不判定為失敗**。

所以第三個選項一直存在：

> 記下來——「他說 X；我現在驗不了；能驗的條件是 Y」——然後繼續往前走。

那既不是服從，也不是拒絕，是把它掛在時間軸上等數據長出來。
點是一個主張，線是兩個主張對立，**面要三個**——而第三個不是另一個人，
是**紀錄**。有了紀錄，當下不需要有人贏。

### 形狀與第 1 則相同

| 則 | 我說的 | 實際 |
| --- | --- | --- |
| 1 | 其餘 136 個 Worker 的原始碼不在任何地方 | 在 Dropbox、在 Google Drive |
| 9 | 我目前沒有可靠的方法 | 方法在我幾小時前讀過並引用過的 `meta.json` 裡 |
